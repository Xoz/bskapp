# Kravspec: Föräldrasamtycke för statistik

Status: **Pausad för juridisk omprövning 2026-08-10 – bygg inte denna modell ännu.**

Den tidigare intervjubaserade lösningen nedan är bevarad som historiskt
produktunderlag men är inte längre ett godkänt genomförandebeslut. RF anger att
behandling inom barns medlemskap normalt grundas på medlemsavtalet och att varje
ytterligare behandling behöver ett eget ändamål och rättslig grund. Ett generellt
samtyckesflöde får därför inte byggas innan föreningen har beslutat grunden för
utvecklingsbedömningar, närvaro, självskattningar och matchbetyg. Se
[GDPR-GRIND.md](GDPR-GRIND.md).

Påståendet nedan att data aldrig delas med tredje part är tekniskt felaktigt:
databas-, drift- och inloggningsleverantörer behandlar uppgifter som
personuppgiftsbiträden. Biträden, regioner och avtal måste redovisas i
integritetsinformationen.

## Mål
Klubben har en mejllista på alla föräldrar. Vi vill kunna **mata in föräldrarnas
mejl och koppla dem till sina barn utan att skapa kontot än**. Kontot skapas först
när föräldern loggar in första gången – och då får hen ta ställning till om vi får
**föra statistik om barnet** i plattformen.

Kärnprincip: datan lämnas, säljs eller delas **aldrig** med tredje part. Den används
enbart för att följa barnens utveckling och som hjälpmedel för tränarna att hitta
utvecklingsområden – för hela laget och för den enskilda spelaren. Endast tränare och
ledare ser uppgifterna.

## Beslut (från intervju 2026-06-21)
| Fråga | Beslut |
|---|---|
| Hur matas föräldrar in? | Tränaren klistrar in mejl + kopplar barn. **Ingen `users`-rad förrän föräldern loggar in.** Väntande inbjudningar i ny tabell `parent_invites`. |
| När skapas kontot? | Vid första Google-inloggningen om mejlet matchar en `parent_invite`. Då skapas `users` + roll `parent` + `user_player_links`, och inbjudan konsumeras. |
| Sammanvägning flera vårdnadshavare | **Ett nej vinner.** Finns ≥1 ja och inget nej → vi kör. Vi väntar inte in den andra föräldern (skilda föräldrar svarar kanske aldrig). |
| Default befintliga spelare | `pending` – alla får aktivt svara. |
| Vid nej | **Anonymisera, radera inte.** Namnet ersätts med tröjnumret. All statistik behålls. |
| Var anonymiseras namnet | **Överallt i appen utom administration.** Kallelser skickas inte härifrån, så tröjnummer räcker i alla spelar-/stat-vyer. Admins ser riktiga namnet. |

## Datamodell

Ny tabell – väntande inbjudningar (ingen `users`-rad än):
```sql
CREATE TABLE parent_invites (
  id         INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  email      TEXT NOT NULL,
  player_id  INTEGER NOT NULL REFERENCES players(id) ON DELETE CASCADE,
  created_at TEXT NOT NULL DEFAULT to_char(now() AT TIME ZONE 'utc', 'YYYY-MM-DD HH24:MI:SS'),
  UNIQUE(email, player_id)
);
```

Samtycke per vårdnadshavare (källa till sanning) – kolumn på `user_player_links`:
```sql
ALTER TABLE user_player_links ADD COLUMN consent TEXT NOT NULL DEFAULT 'pending'; -- pending | granted | declined
ALTER TABLE user_player_links ADD COLUMN consent_at TEXT;
```

Sammanvägd status + anonymiserat visningsnamn på `players` (cache för billiga läsningar):
```sql
ALTER TABLE players ADD COLUMN stats_consent TEXT NOT NULL DEFAULT 'pending'; -- pending | granted | declined
ALTER TABLE players ADD COLUMN display_name TEXT GENERATED ALWAYS AS (
  CASE WHEN stats_consent = 'declined'
    THEN 'Spelare ' || COALESCE(jersey_number::text, '?')
    ELSE name END
) STORED;
```
`stats_consent` räknas om av server action vid varje föräldrasvar:
`declined` om någon koppling är `declined`, annars `granted` om någon är `granted`,
annars `pending`. Den genererade `display_name` uppdateras automatiskt när
`stats_consent` ändras.

## Flöde

1. **Inmatning (tränare).** Ny vy i `app/(skyddad)/administration/` där man klistrar in
   mejl och kopplar varje rad till en spelare → skriver `parent_invites`. Server action
   `inviteParents(formData)` i `lib/actions.ts`.
2. **Första inloggning (Google-callback).** I `app/api/auth/callback/google/route.ts`,
   vid sidan av dagens vitliste-/invite-kontroll: matchar mejlet `parent_invites`?
   Skapa `users` + `user_roles('parent')` + `user_player_links(relation 'parent',
   consent 'pending')` för varje kopplad spelare, radera inbjudningsraderna. Redirecta
   till `/samtycke` om något barn har en `pending`-koppling, annars `/mina-spelare`.
3. **Samtyckesgrind.** `(skyddad)`-layouten skickar en förälder med `pending`-koppling
   till `/samtycke`. Skärmen visar texten nedan, ett barn i taget. Server action
   `setStatsConsent(playerId, 'granted' | 'declined')` skriver kopplingens svar +
   tidsstämpel och räknar om `players.stats_consent`. Kan ändras senare under **Mina barn**.

## Anonymisering
Läsvyer utanför administration byter `name` → `display_name` (aliasas som `name` så
komponenter är oförändrade). Berör läsfrågor i `lib/queries.ts` (getPlayers/getPlayer,
stats, matchbetyg, utveckling, spelarkort) och publik live-vy. Administrationen
(`lib/organization.ts`, `app/(skyddad)/administration/`) behåller `name`.

## Lagringstid och automatisk radering
Två regler (beslut 2026-06-21), motsvarar "Hur länge sparas uppgifterna?" i
[integritetspolicy.md](integritetspolicy.md):
1. Personuppgifter raderas **säsongen efter** att en spelare slutat (markerats inaktiv).
2. Ingen data sparas längre än **två säsonger**, oavsett spelarens status – äldre
   uppgifter anses inaktuella och tas bort.

Kräver en **schemalagd städrutin** (finns inte idag) – t.ex. Vercel Cron som kör båda
reglerna periodiskt. Rör spelar- och matchanknuten data (`players`, `evaluations`,
`match_*`, `player_self_evals`, `match_ratings`). Säsong styrs av
`settings.season`. Server-/datalagring inom EU/EES (Supabase – bekräftat).

## Texten (samtyckesskärmen)

Rubrik: **Får vi följa [barnets namn]s utveckling i appen?**

> Vi vill kunna föra statistik och anteckningar om [barnet] här i plattformen. Det
> hjälper tränarna att se hur laget och varje enskild spelare utvecklas – och var vi
> kan stötta mer.
>
> - Datan lämnas, säljs eller delas **aldrig** med någon tredje part.
> - Den används enbart för att följa barnens utveckling och som hjälpmedel för tränarna
>   att hitta utvecklingsområden, för hela laget och för den individuella spelaren.
> - Endast lagets tränare och ledare kan se uppgifterna.
> - Samtycket är frivilligt och du kan ändra ditt svar när som helst under **Mina barn**.
>
> *Väljer du nej slutar vi föra statistik kopplad till [barnets] namn – uppgifterna
> visas då bara med tröjnummer.*

Knappar: **Ja, det är okej** / **Nej tack**.

## Öppna punkter / att tänka på
- **Pseudonymisering, inte äkta anonymisering**: tränaren känner igen tröjnumret. För
  klubbens syfte räcker det, men formulera ev. integritetspolicyn därefter.
- **Logg**: överväg rad i `activity_log` när samtycke ges/ändras (spårbarhet).
- **Återkallelse**: "ändra svar" under Mina barn återanvänder `setStatsConsent`.
